Sicon Sage 200 WebAPI · Access Request

What we need to connect GymAxis to the
Pulse Fitness Test environment.

A short, specific brief for Pulse Fitness's Sicon / Sage 200 administrator. Read time: 90 seconds. Action required: create one read-only API user and confirm three details.

§1 The ask, in one sentence

Please create a dedicated, read-only Sicon WebAPI user against the Pulse Fitness Test company on service.pulsefitness.com, with access to the Service Case and Service Appointment endpoints. GymAxis will use these credentials only to read fault & engineer-job data into our maintenance platform — no writes to your live Sage 200 environment, ever, until we both sign off on a UAT plan.

§2 Exactly what to create in Sage

In Sage 200 → Sicon WebAPI → Maintain WebAPI Users, create:

WebAPI usernamegymaxis-readonly
PasswordGenerated by you · sent to GymAxis via a password-manager share link or password-protected PDF (not plain email).
CompanyPulse Fitness Test
Authentication schemeHTTP Basic (per Sicon WebAPI standard)
Account stateEnabled · password set to never expire for the duration of integration testing (we'll rotate together at go-live)

§3 Permissions — least-privilege scope

Only these endpoints are required. Everything else can stay locked down.

EndpointMethodsWhy we need it
/api/SMConnectivity/Ping GET Health check — we hit this every 60 s.
/api/service/cases & /api/service/cases/{id} GET Read existing service cases & their detail.
/api/service/case-types · case-tracking-statuses · priorities GET Pull dropdown lists so GymAxis maps to Sicon's exact values.
/api/service/trackingnotes/{id} GET Read engineer progress notes on a case.

Note: at this stage we are not requesting any POST/PUT/DELETE access. When we're ready to write back to Sicon (engineer notes, time-bookings), we'll submit a second, narrower request for those specific endpoints only.

§4 What we do not need (reassurance)

To keep the scope as small as possible, we are explicitly not requesting:

  • Access to your Live Sage 200 company — Test only at this stage.
  • Access to Finance ledgers (Sales/Purchase/Nominal/Cashbook) — out of scope.
  • Access to Stock, Manufacturing, SFDC mobile endpoints — these are factory-floor controllers, not relevant to gym maintenance.
  • Any write access during the initial integration window — read-only only.
  • Any of your customer or supplier personal data beyond what's already in service cases — we don't pull master records.

§5 Three details to confirm with the user/password

Company IDThe numeric companyID for "Pulse Fitness Test" (usually 1–10).
IP allowlistIf the WebAPI is IP-restricted, please add GymAxis production egress IPs (we'll send under separate cover when you confirm).
Rate limitsAny per-user request-rate cap we should respect (we'll default to ≤ 2 requests/second per controller if unspecified).

§6 Our security commitments to Pulse

Credential storage
Stored encrypted at rest in a UK-hosted secrets vault. Never logged, never appears in error reports.
Transport
TLS 1.3 only. We pin the Sicon hostname & reject downgraded connections.
Audit trail
Every Sicon call is logged with timestamp, endpoint, status, and the GymAxis operator who triggered it. We'll share the log on request.
Rotation
We'll rotate this credential jointly at the end of integration testing, and at any cadence Pulse requires thereafter.
Breach response
If we suspect the credential is compromised, we notify Pulse IT inside 4 hours and stop using it.
Data residency
Any data fetched from Sicon stays inside the GymAxis UK tenant boundary — no offshoring, no third-party processors.
