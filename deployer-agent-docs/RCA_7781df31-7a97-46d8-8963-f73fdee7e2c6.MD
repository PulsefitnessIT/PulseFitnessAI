# RCA — MOD faults not visible on Pulse Service Desk

**App:** PulseFitness CRM (fitness-ai-migrate) · DB: `rbac-modules-test_database` · run `7781df31`
**Mode:** Read-only production debug. No data changed.

## Verdict
The `svc_cases` **ARE created** for every MOD fault — they are NOT missing, NOT in the wrong source/status. They are filed under a **separate synthetic tenant** `organization_id = "bfpo-mod-org"`, while the Pulse Service Desk list endpoint `GET /api/svc/cases` hard-scopes every query to the **caller's own** `organization_id` (the Pulse org). Pulse org ≠ `bfpo-mod-org`, so the desk never returns them. This is a **tenant/org scoping mismatch**, not a creation failure or a status/provider filter.

## Code proof
- `backend/routes/bfpo.py`: `BFPO_ORG_ID = "bfpo-mod-org"`; `_bridge_mod_fault_to_bfpo(issue)` (line 229) inserts the svc_case with `organization_id = BFPO_ORG_ID`, `bfpo: True`, `source: "mod_fault"`. A reconcile job `_ensure_mod_faults_bridged()` keeps every MOD fault mirrored there.
- `backend/routes/svc/cases.py` `list_cases` (GET `/api/svc/cases`): `q = {**_of(user)}` where `_of(user) = {"organization_id": user.organization_id or user.service_org_id}`. Every desk query is hard-filtered to the caller's org. There is **no** branch that unions in `bfpo-mod-org` cases, so MOD/BFPO cases can never surface on the standard Service Desk.

## Root cause (one line)
MOD faults are bridged into `svc_cases` under the hard-coded BFPO tenant `organization_id="bfpo-mod-org"`, but the Pulse Service Desk `GET /api/svc/cases` scopes strictly to the signed-in user's own org — so the Pulse desk (org `3ece2d0c…`/`d19de469…`) never sees any of the 10 MOD cases. Creation is fine; it's an org-scoping/visibility gap.

## Suggested fix (Code — E1; read-only requirement honored, no data edited)
Pick one, consistent with the "external-provider jobs read-only on the Pulse desk" requirement:
1. **Desk-side union (preferred, least data churn):** in `list_cases` (and the desk dashboard/KPI aggregations), when the caller is a Pulse service-desk org, widen the org filter to also include `organization_id="bfpo-mod-org"` MOD cases (e.g. `{"$or":[{"organization_id":callerOrg},{"organization_id":"bfpo-mod-org","source":"mod_fault"}]}`), and render those as read-only when they carry a supplier_case / external routing. Apply the same union to `get_case`/events so detail opens.
2. **Bridge-side:** have `_bridge_mod_fault_to_bfpo` file the svc_case under the Pulse service org (keeping a `bfpo:true` flag + `mod_site_id` for the BFPO portal to filter on) instead of a separate synthetic tenant, and backfill the existing 10 docs.

Either path needs a redeploy. No secret, tier, infra, or DB-data problem is involved.
