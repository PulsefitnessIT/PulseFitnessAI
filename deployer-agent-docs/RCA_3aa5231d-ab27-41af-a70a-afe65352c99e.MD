# RCA — Devon & Somerset Fire & Rescue PPM jobs show no machines + no treadmill form

**DB inspected (read-only):** `rbac-modules-test_database` (prod), run `3aa5231d-ab27-41af-a70a-afe65352c99e`.
**Subject:** engineer William Ollis — `users.id = ef4fd847-fc3a-450f-84bf-af89bce4c06d`, `organization_id = 3ece2d0c-57ea-4acd-a6b4-d748478ed117` (Pulse operator org).

## Direct answers to the 4 deliverable questions

**(a) Are `equipment_ids` populated on the PPM cases?** — YES, they are populated (not empty).
- SVC-00013 (`0ffad7be-...`), site "Nether Stowey Fire Station" → 4 equipment_ids
- SVC-00014 (`4eaf0d9d-...`), site "Bridgwater Fire Station" → 9 equipment_ids
- SVC-00015 (`d1db2ef6-...`), site "Burnham-on-Sea Fire Station" → 7 equipment_ids
- The matching `ppm_schedules` doc (`9b57320d-...`) carries the SAME 4 equipment_ids. So empty equipment_ids is NOT the bug.

**(b) Under which org is the equipment stored, vs the case's org? — ORG-SCOPING MISMATCH.**
- Case `organization_id` = `3ece2d0c-...` (Pulse **operator** org).
- Case `ppm_customer_org_id` = `e8bd4162-94f5-465e-b2ab-357763e205ec` (D&S **customer** org).
- The 4 equipment rows referenced by SVC-00013's `equipment_ids` ALL have `organization_id = e8bd4162-...` (the customer org), `site_id = f90714be-...`.
- `ppm_schedules` doc `organization_id` = `e8bd4162-...` (customer org) — i.e. the schedule is scoped to the customer org, but the generated case is scoped to the operator org `3ece2d0c-...`.
- `equipment.distinct(organization_id)` = `["30664e31-...", "e8bd4162-...", "mod-site-british-army-training-unit-kenya"]` — note `3ece2d0c` (the operator/case org) is NOT among them, so ANY equipment lookup filtered by `case.organization_id` returns ZERO rows.

**(c) Is any equipment typed as a treadmill? — YES, correctly typed.**
- Equipment `d03f17a9-...` = name "Vision - T600 - Treadmill", `equipment_type = "Treadmill"`, org `e8bd4162-...`, site `f90714be-...`.
- Others at that site: "Rower", "Upright Bike", "Bench". Treadmill typing is CORRECT — missing treadmill typing is NOT the bug.

**(d) Do `svc_work_visit_machines` rows exist for the PPM case, and are they populated? — NO rows for the PPM case; existing rows (other cases) are generic placeholders.**
- `svc_work_visit_machines.find({case_id: "0ffad7be-..."})` → **count 0**. The bulk-PPM backfill never created per-machine visit rows for William's PPM cases.
- Collection total = 41 rows, all for OTHER (non-PPM) cases, e.g. case `52995f0d-...`, and they are generic placeholders: `asset_name = "6 machines"`, `asset_type = null`, no `equipment_id` field, org `3ece2d0c-...`. So even where rows exist they are not per-machine/typed.

## Root cause (two compounding faults)
1. **Org-scoping mismatch on the equipment join.** The PPM cases are written under the operator org (`3ece2d0c`), but the equipment (and the ppm_schedule) live under the customer org (`e8bd4162` = `ppm_customer_org_id`). Any machine/equipment resolution that filters by the case's `organization_id` finds nothing → "no machines to service", and the treadmill (correctly typed) never surfaces → no calibration form. The equipment should be resolved by `equipment_ids` scoped to `ppm_customer_org_id`, not `organization_id`.
2. **Missing `svc_work_visit_machines` rows.** The bulk-PPM wizard + backfill did not materialise per-machine work-visit rows for the PPM cases (0 rows), so any UI reading the machine list from that collection renders empty regardless of the join.

Neither "empty equipment_ids" nor "missing treadmill typing" is the cause — both are correct in the data.

## Fix (owned by E1 / code + data backfill — NOT a deployment issue)
- **Code:** make the PPM case → equipment resolution join scope by `equipment_ids` under `ppm_customer_org_id` (customer org), not the case's `organization_id` (operator org). Audit any other equipment/asset lookup on PPM cases for the same operator-vs-customer org filter bug.
- **Data backfill:** generate `svc_work_visit_machines` rows for the existing PPM cases from each case's `equipment_ids` (resolving real `asset_name`/`asset_type`/`equipment_id` from the equipment collection), replacing the generic "6 machines"/null-type placeholder pattern.

All findings are from read-only `mongo_query`; no data was modified.
