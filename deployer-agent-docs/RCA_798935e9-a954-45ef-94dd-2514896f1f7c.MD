Routing logic (`frontend/src/utils/moduleHome.js :: resolveHomePath`, evaluated on the LOGIN payload):
```
if (is_external_engineer && !is_master_admin && !is_pulse_admin) return '/svc/engineer';  // intended
if (['engineer','lead','staff'].includes(bfpo_role))             return '/bfpo';           // fallback Jimmy hits
```
`is_external_engineer` is **computed** by `utils/esp_engineer.is_external_engineer(user)` → for Jimmy returns **True** (`mod_estate_supplier_id` set, not the in-house id). On THIS build it is injected into BOTH payloads:
- login payload `_build_login_user_payload` (auth.py line 337)
- `/auth/me` payload `get_me` (auth.py line 1108)

So on THIS build the backend emits `is_external_engineer:true` and `resolveHomePath` SHOULD return `/svc/engineer`. The observed `/bfpo` landing therefore means the **client that logged in did NOT receive/act on `is_external_engineer` with the ESP-first precedence** — i.e. it was served by a build/bundle where that field is missing from the login payload and/or `resolveHomePath` lacks the ESP-first branch. Once on `/bfpo`, the ESP engineer endpoints that power faults / "My customers" / "Equipment" are never called → symptoms #2 and #3 follow directly from #1.

## ROOT CAUSE
This is **NOT a data problem and NOT domain binding.** The production data for Jimmy is complete and internally consistent — single user doc, a matching svc_engineers row, a correct `mod_estate_suppliers → suppliers → organizations/equipment` bridge (all string UUIDs), and an assigned fault on his site. On the ESP-aware build, `is_external_engineer(user)=True` routes him to `/svc/engineer` and `engineer_job_scope`/`esp_site_ids` resolve his site, his assigned fault, and his 167 machines correctly. **I found NO mismatch between the id fields the code uses (`esp_engineer.is_external_engineer`, `engineer_queue`) and the production data shapes.**

The failure is a **build / version skew between the two deployments that share this DB.** Jimmy logs in via **modservice.pulsefitness.com**, which I cannot inspect; the symptoms (lands on `/bfpo` instead of `/svc/engineer`, no ESP faults, empty ESP Quick Actions) are exactly what you get when the deployment serving him runs an OLDER frontend/backend build in which the login payload omits `is_external_engineer` and/or `resolveHomePath` lacks the `is_external_engineer → /svc/engineer` precedence (so the next rule, `bfpo_role=='engineer' → /bfpo`, wins). The "sometimes" is consistent with a stale **Cloudflare/R2 cached frontend bundle** vs a fresh one, or inconsistent builds across the two deployments. Evidence on THIS deployment (repeated `/bfpo/alerts`, zero `/svc/engineer/*`) shows the `/bfpo` mis-landing is reproducing against this DB too.
