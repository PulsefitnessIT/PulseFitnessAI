# RCA — Imported estates not pulling through to CRM (PulseFitness.ai Aftersales)

**Scope:** Read-only production diagnosis. DB: `rbac-modules-test_database` (deployed Mongo), run `9be5b76d-f96a-4f37-89fb-2c72328ebe1f`.
**Endpoint under investigation:** `POST /api/master-admin/bulk-import/backfill-crm` (`_resolve_operator_org` + backfill filter in `backend/routes/master_admin_bulk_import.py`).

## Verdict
**Root cause = the backfill account_type allow-list does NOT match the account_type values the MOD estates actually carry in production.** Backfill bridges orgs whose `account_type` is in `[pulse_pro, lite, mod, full]` or null. The imported MOD estates carry `account_type = "mod_org"` / `"mod_site"`. `"mod_site"` / `"mod_org"` ≠ `"mod"`, so these estates fail condition (b) and are silently skipped — **even when they own equipment**.

The other three hypotheses were checked and are NOT the cause (evidence below).

---

## 1. OPERATOR FLAG — HEALTHY (not the bug)
`organizations.count({is_operator_company:true})` = **1**, and it is the expected operator:
- id `3ece2d0c-57ea-4acd-a6b4-d748478ed117`, name **Pulse Fitness Ltd**, account_type `pulse_pro`.

So `_resolve_operator_org` resolves correctly; there is no fallback-to-admin-org happening for operator resolution.

## 2. IMPORTED ORGS — condition analysis (this is where it breaks)

**Key finding:** `British Army Training Unit Kenya` owns **107 pieces of equipment** — it satisfies (a) — yet is excluded purely because its `account_type = "mod_site"` is not in the allow-list. Confirmed: `crm2_companies.count({linked_organization_id:"mod-site-british-army-training-unit-kenya"})` = **0**.

`distinct(account_type)` across all orgs = `["lite","mod_org","mod_site","pulse_pro"]` (plus null). The strings `"mod_org"`/`"mod_site"` are what production uses; the code's allow-list expects `"mod"`. That is the mismatch.

The MOD HQ orgs (army/raf/navy) have 0 sites and 0 equipment, so they fail condition (a) too — their non-bridging is expected (parent HQ records with no estate data), independent of the type bug.

---

## Conclusion
- ❌ Operator flag missing — DISPROVEN (exactly 1, correct org).
- ❌ crm2_companies mis-stamped to non-operator — DISPROVEN for estates (Devon/Penkridge correctly stamped to operator); only the operator's own self-company is mis-stamped (minor).
- ❌ CRM user in a different org — DISPROVEN (all CRM users in operator org).
- ✅ **CONFIRMED: imported MOD estates fail the backfill account_type filter.** Production estates carry `account_type` `"mod_org"`/`"mod_site"`, but the allow-list checks for `"mod"`. Estates with real equipment (e.g. Kenya, 107 items) are therefore skipped and never appear in the CRM.

## Recommended fix (source — for E1 to apply, not applied here)
In `backend/routes/master_admin_bulk_import.py` (the backfill eligibility filter, near the `_resolve_operator_org` block, lines ~761–771 and the account_type gate):
1. **Widen the account_type allow-list** to include the real MOD values: add `"mod_org"` and `"mod_site"` (and confirm whether `"full"` should really be `"full"` vs an actual stored value). Preferably normalize with a prefix/`startswith("mod")` or a mapping set rather than exact-match on `"mod"`.
2. Re-run the "Sync" backfill after the fix; verify the Kenya estate (and any other `mod_*` estate owning sites/equipment) then appears with `organization_id = 3ece2d0c-57ea-4acd-a6b4-d748478ed117`.
3. (Optional, secondary) Correct the mis-stamped self-company row `Pulse Fitness Ltd` (crm2_companies id `ee1dcb13-99c8-48cd-bece-dd128aef57f0`) whose `organization_id` = admin org `d19de469` instead of the operator org.
