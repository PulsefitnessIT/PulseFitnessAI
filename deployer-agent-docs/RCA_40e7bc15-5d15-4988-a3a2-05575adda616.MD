# RCA — PulseFitness CRM: "CRM module switch cannot be turned off" (org 3ece2d0c)

Mode: READ-ONLY production debug. Active prod run: `40e7bc15-5d15-4988-a3a2-05575adda616`.
DB: `rbac-modules-test_database`, collection `organizations`.

## Problem statement
On live pulsefitness.ai, Master Admin → Organisations → "Pulse Fitness Ltd" → Modules, the main CRM
switch snaps back ON after being turned off. PUT `/api/master-admin/organizations/{org_id}/features`
with `{"modules":{"crm":{...cfg,"enabled":false}}}` returns 200 but `modules.crm.enabled` stays `true`.
Reporter says the same call persists `enabled:false` in preview.

## ROOT CAUSE — `routes/master_admin_orgs.py`, `update_org_features` (PUT /features), lines ~489–495

```python
if m_key == "crm":
    if "business_enabled" in cfg:
        entry["business_enabled"] = bool(cfg["business_enabled"])
    if "leisure_enabled" in cfg:
        entry["leisure_enabled"] = bool(cfg["leisure_enabled"])
    if entry.get("business_enabled") or entry.get("leisure_enabled"):
        entry["enabled"] = True          # <-- overrides the explicit enabled:false
```

The handler force-sets `crm.enabled = True` whenever `business_enabled` OR `leisure_enabled` is truthy,
**ignoring the explicit `enabled:false` the user sent.** The frontend `FeatureControlPanel.js` main CRM
switch (line ~222) sends `{...cfg, enabled:false}` — i.e. it spreads the existing config, so the disable
request always carries whatever mode flags the org has. Any org with a CRM mode still ON therefore can
never be disabled from the main switch: the server flips `enabled` back to `true` and returns 200.

I reproduced the exact handler merge logic in a sandbox against the real doc values:

- **A. Current doc (both modes false), main toggle off →** `enabled: False` (persists correctly).
- **B. business_enabled=true, main toggle off `{...cfg, enabled:false}` →** `enabled: True` ← **the snap-back**.
- **C. modes stored as the string `"false"`, main toggle off →** `enabled: True` (because `bool("false")` is `True`) — the type trap; not active here but latent for any string-valued org.
- **D. no mode flags in doc + frontend leisure default-on sends `leisure_enabled:true` →** `enabled: True`.

This is also a **one-way latch**: the condition only ever forces `enabled → true`, never `→ false`. So
once `enabled` is stuck true and the modes are later turned off, nothing clears `enabled`. That is exactly
this org's current state (audit 16:14:08: business went true→false but `enabled` stayed true).

### Contributing factors
- **Frontend default-on for leisure** (`FeatureControlPanel.js` ~line 250: `checked={cfg.leisure_enabled !== false}`)
  renders the Gym/leisure sub-switch as ON when the flag is missing/undefined, and the mode-toggle handlers
  only ever force `enabled: true` — compounding the latch.
- **Preview vs prod:** the deployed prod image (this run) contains the buggy code above. If preview now
  persists `enabled:false`, preview is running newer/fixed code that has NOT yet been redeployed to prod.
  (I could not inspect preview's source; this is inferred from the reporter's statement + the prod code.)

Given the CURRENT doc (both modes already false), the prod code *would* now persist a main-toggle-off
(scenario A) — provided the frontend's in-memory `org.modules.crm` isn't stale from before the modes were
turned off. The historical and general failure is scenario B, which matches the reported symptom while
business mode was on (2026-07-03 → 2026-11-12).

## Suggested fix (code, E1 — then redeploy)
1. In `update_org_features`, make the explicit `enabled` authoritative: do NOT force `enabled=True` from
   mode flags. If honoring the "mode implies enabled" convenience, only apply it when the caller did NOT
   explicitly send `enabled:false`. Conversely, when `enabled:false` is sent, also clear
   `business_enabled`/`leisure_enabled` so the latch can't re-arm.
2. Coerce mode flags defensively so a stray string can't be truthy (treat `"false"`/`"0"` as false).
3. Frontend `FeatureControlPanel.js`: the main CRM "off" payload should set `business_enabled:false` and
   `leisure_enabled:false` alongside `enabled:false`; and fix the leisure default-on (`!== false`) so a
   missing flag isn't treated as ON.
4. (Optional data repair) This org is currently latched at `crm.enabled=true` with both modes false. With
   the fixed code a single main-toggle-off clears it; alternatively set `modules.crm.enabled=false` directly.
