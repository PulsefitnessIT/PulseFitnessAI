# RCA — BATUK MOD faults: Pulse Fitness MOD desk received no emails

**Deployment:** pulse-mod-estate (MODService @ https://modservice.pulsefitness.com)
**Active run:** c77b306f-a3bb-40c4-a62a-6a5b0ed0b786 · DB `rbac-modules-test_database` (shared with pulsefitness.ai)
**Mode:** read-only RCA, no writes.

## TL;DR — ROOT CAUSE
Every MOD-fault email for BATUK on 9 Nov 2026 was **attempted and REJECTED by Resend** with `ResendError('API key is invalid')` — including the send to the Pulse MOD desk `MODService@pulsefitness.com`. The configured **`RESEND_API_KEY` value is invalid** (present in env, but Resend rejects it), so *all* outbound email from this deployment is currently failing. This is a secret-value problem, **not** the recipient-validation flag.

The user's leading hypothesis is **disproven**: `ENFORCE_EMAIL_RECIPIENT_VALIDATION` is **not set** (defaults `"false"` → `validate_email_recipient` is a no-op). No HTTPException 400 was raised and nothing was swallowed by `_send_mod_fault_notifications`; the send reached Resend and Resend rejected it.

The current (9-Nov) failures are **API-key-invalid**, not domain errors.

### Secrets (active run)
- `ENFORCE_EMAIL_RECIPIENT_VALIDATION` — **ABSENT** → code default `false` → validation gate is a no-op. (web_security.py L188-190, L224: `if not _ENFORCE_RECIPIENT_VALIDATION: return`.)
- `MOD_SERVICE_EMAIL` — **ABSENT** → falls back to default `MODService@pulsefitness.com` (which is exactly the recipient used — correct).
- `MOD_SENDER_EMAIL` — present/non-empty → resolves to `modservice@modservice.pulsefitness.com` (the From shown — correct).
- `SENDER_EMAIL` — present/non-empty.
- `RESEND_API_KEY` — present/non-empty, but **value rejected by Resend as invalid** (proven by logs + audit). list_secrets cannot read the value; validity proven from the Resend error.

### Why the badge/log is misleading
`notified_recipients` and the green "Sent to Inda Fitness" badge are written **regardless of delivery outcome**. In `_send_mod_fault_notifications`, the `delivered` flag is only attached when `send_email` is actually invoked; on these issues the recipients were treated as "already emailed" by the earlier auto-dispatch path, so the proof-log was recorded with **no `delivered` key** — i.e. the UI shows "Sent" even though Resend rejected the real send. So "Sent to Inda Fitness" is NOT evidence of delivery; Inda's email failed too.

## FIX
1. **User — Secrets:** Replace `RESEND_API_KEY` in Deployment Panel → Secrets with a valid, active Resend API key, then redeploy. This is the direct cause and unblocks ALL outbound email (MOD desk, supplier, and MOD-contact notifications).
2. **User — Resend (3rd-party):** In the Resend dashboard confirm the key is active/not revoked and that the `modservice.pulsefitness.com` sending domain is verified (SPF/DKIM) for the `modservice@modservice.pulsefitness.com` From address. Shared-DB caveat: if the pulsefitness.ai deployment also sends MOD mail, check its `RESEND_API_KEY` too.
3. **Code (optional, E1):** The "Sent to <supplier>" badge and `notified_recipients` proof-log are written even when Resend rejects the send, so operators see "Sent" on an email that never delivered. Gate the badge/log on the actual `send_email` result (and surface failed sends). Not the cause of the outage, but it masked it.

Note: the invalid-key failure is an env/secret + external-service issue — not reproducible in the eph sandbox (no live Resend credential), so it was diagnosed from production logs + the email audit collection, which is authoritative.
